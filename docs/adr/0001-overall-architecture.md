# ADR 0001: Гибридная архитектура — расширение + локальный бэкенд

## Status

Accepted, 2026-05-17

## Context

Инструмент должен:

1. Незаметно проходить тесты в Moodle (минимум следов на стороне сервера).
2. Поддерживать три режима взаимодействия — assist, full-auto, step-by-step.
3. Использовать AI для генерации ответов (Gemini Pro + локальная Gemma).
4. Хранить историю попыток локально.
5. Работать на машине пользователя без облачных компонент.

Рассматривались три варианта компоновки.

### Вариант A: Только MV3 расширение

Всё в JS внутри браузера. Расширение само парсит Moodle, само вызывает
Gemini, само "решает".

**Плюсы:** максимально stealth (живёт в реальной сессии пользователя, тот
же fingerprint, те же куки); никакой отдельной установки; один артефакт.

**Минусы:**
- Локальную LLM (Gemma через Ollama) запустить из расширения нельзя без
  локального HTTP-сервера → всё равно потребуется backend для Phase 1.5.
- Ключ Gemini API лежит в `chrome.storage` — доступен через DevTools и
  утекает в backup профиля.
- CORS-политика: Gemini API сам по себе разрешает прямые запросы, но
  любой проксирующий слой/локальная модель добавляет точки отказа.
- engine-режим с undetected-chromedriver невозможен — это Python-only.

### Вариант B: Только Python с Playwright

Standalone скрипт, открывает свой Chromium, делает всё сам.

**Плюсы:** мощный engine (undetected-chromedriver, vision, ML), один
язык (Python), легко тестировать.

**Минусы:**
- Открывается отдельный Chromium — не та сессия, где пользователь
  обычно ходит → проблемы с MFA, "новое устройство" уведомлениями.
- Assist-режим в чужом окне неудобен — пользователь работает в своём
  Chrome, а ответы AI видит в отдельном окне или в терминале.
- Менее stealth — fingerprint Playwright-Chromium отличим от реального.

### Вариант C: Гибрид (выбран)

Расширение делает UX и assist-режим в реальном Chrome пользователя.
Бэкенд делает AI, хранилище и опциональный engine-режим. Связь через
HTTP+WS на localhost.

## Decision

**Принят вариант C — гибрид.**

| Компонент | Ответственность |
|---|---|
| MV3 Extension | Парсинг DOM Moodle, overlay подсветки, popup настроек, передача в backend, выполнение клика в assist/step-by-step режимах |
| Local Backend | AI-провайдеры (Gemini, Ollama), история (SQLite), кеш, engine-режим (undetected-chromedriver), API для расширения |
| Engine (часть backend) | Только для full-auto: подключается по CDP к Chrome пользователя или открывает свой stealth-Chromium |

Связь — REST + WebSocket на `127.0.0.1:8765`. Подробности контракта — см.
[0005-extension-backend-communication.md](0005-extension-backend-communication.md).

## Consequences

### Положительные
- Каждый компонент использует лучший инструмент: JS для DOM, Python для AI/ML.
- Stealth максимален — основной поток идёт через настоящий браузер пользователя.
- Ключ Gemini защищён — не покидает backend.
- Engine-режим даёт fallback на случай, если Moodle обновит UI и расширение
  временно сломается — engine не зависит от селекторов в реальном времени.

### Отрицательные
- Установка сложнее: ext + Python + опционально Ollama.
- Два кодбейза (TS + Py) — две системы сборки, два набора тестов.
- Нужно синхронизировать модели данных между ext и backend (решается
  кодогенерацией из OpenAPI или ручным дублированием — см. ADR 0005).

### Mitigations
- README с инструкцией в 5 шагов установки.
- Docker Compose для backend в Phase 4.
- `docs/specs/question-model.md` как single source of truth для типов.

## Alternatives considered

См. варианты A и B выше. Отдельно отвергнут:

- **Native messaging** (расширение запускает Python через stdin/stdout) — сложнее
  установка (manifest регистрации в системе), хуже отладка, нет WS-стрима.
  Localhost-HTTP проще и кросс-платформенно.
- **Облачный backend** — нарушает требование "локальность" и privacy (куки
  LMS не должны покидать машину пользователя).
