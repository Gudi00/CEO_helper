# ADR 0004: Стратегия доступа к сессии LMS

## Status

Accepted, 2026-05-17

## Context

Чтобы автоматизация работала, нужна аутентифицированная сессия в Moodle.
Варианты, как её получить:

| Способ | Где живёт сессия | Видно ли пароль инструменту | Stealth |
|---|---|---|---|
| Логин по логину/паролю в .env | В .env (открытый текст) | Да | Низкий — отдельная сессия, новое устройство |
| Manual login в открывшемся окне Playwright | В `storage_state.json` | Нет (вводит пользователь) | Средний — отдельный браузер |
| CDP attach к реальному Chrome | В системе, как обычно | Нет | Максимальный — настоящая сессия |
| Cookie экспорт расширением | В файле/в backend | Куки (но не пароль) | Зависит от того, куда применяются |

LMS BSUIR может иметь SMS/email-уведомление о новом устройстве или о
повторной логин-попытке. CDP-подход избегает их полностью.

Расширение по природе уже сидит в реальной сессии пользователя — для
assist/step-by-step режимов отдельная стратегия не нужна, ext просто
живёт в Chrome.

Проблема возникает для **engine-режима** (full-auto через
undetected-chromedriver): bots-driver запускает свой Chromium процесс.

## Decision

**Поддерживаем три стратегии для engine-режима. По умолчанию — CDP attach.**

### Стратегия A: CDP attach (по умолчанию, recommended)

```bash
# Пользователь запускает свой Chrome с CDP портом:
google-chrome --remote-debugging-port=9222 \
              --user-data-dir=$HOME/.config/google-chrome-cdp
```

Backend подключается через `undetected_chromedriver.Chrome(options=opts)`
с `debugger_address="127.0.0.1:9222"`. Использует существующие куки,
fingerprint, расширения пользователя.

**Когда использовать:** дефолт для full-auto, когда пользователь не против
запускать Chrome с флагом.

**Pros:**
- Максимальный stealth — буквально та же сессия, тот же fingerprint.
- Нет повторных логинов, нет уведомлений о новом устройстве.
- Работает с MFA (пользователь уже залогинен).

**Cons:**
- Требует от пользователя перезапустить Chrome с флагом (или иметь
  отдельный shortcut). Mitigation: README с инструкцией, опционально —
  systemd-user сервис.
- Использует отдельный профиль (`--user-data-dir`), иначе конфликтует с
  обычным Chrome. Решение: README указывает создать копию профиля.

### Стратегия B: Manual login + storage_state

Backend через Playwright/undetected открывает Chromium, пользователь
вводит логин/пароль/MFA вручную в окне. После успешного логина куки
сохраняются в `~/.config/lms-tool/storage_state.json` для будущих
запусков.

**Когда использовать:** если пользователь не хочет/не может перезапустить
основной Chrome.

**Pros:**
- Не нужно ничего настраивать в своём Chrome.
- Пароль не покидает форму логина LMS, в инструмент не попадает.
- `storage_state.json` живёт долго (пока LMS не инвалидирует).

**Cons:**
- Менее stealth — другой fingerprint, LMS может уведомить "новое устройство".
- При истечении сессии — повторный manual login.

### Стратегия C: Cookie экспорт расширением

Расширение читает `MoodleSession` cookie из своего окна и POST-ит её на
`/api/session/import-cookies`. Backend применяет к своему driver-контексту.

**Когда использовать:** редко. Гипотетически — если CDP недоступен (например,
пользовательский Chrome устарел или политика запрещает).

**Pros:**
- Не требует флагов запуска Chrome.
- Работает в любом окружении.

**Cons:**
- Расширение должно иметь `cookies` permission → лишний слой при ревью
  расширения в Web Store.
- Куки в HTTP-теле POST — теоретически могут попасть в локальные логи.
- Fingerprint всё равно отличается → меньше stealth.

### Что делает само расширение (для assist / step-by-step)

Расширение уже сидит в реальной сессии. Никакая стратегия доступа не
нужна — content script читает DOM текущей страницы, popup ждёт активного
квиза. Backend получает только нормализованные вопросы (без cookies).

## Consequences

### Положительные
- Три способа покрывают все сценарии пользователя.
- Дефолт (CDP) — самый stealth, идеален для основного use case.
- Пароль никогда не попадает в .env — снижение security risk.

### Отрицательные
- Три реализации в `backend/src/automation/access/` — больше кода.
  Mitigation: общий интерфейс `SessionAccess.acquire() -> WebDriver`.
- Документация должна чётко объяснять trade-offs пользователю.

## Alternatives considered

### Логин/пароль в .env
Отвергнуто. Хранить пароль на диске — anti-pattern. Если пользователь
сам захочет — может скриптом эмулировать вход через requests на
`/login/index.php`, но это не часть основной поставки.

### OAuth / SSO
Moodle BSUIR использует свою форму логина, OAuth не предоставляет.
Не применимо.

### Browser profile cloning
Скопировать профиль пользователя в отдельный `--user-data-dir` и
запустить там undetected. Технически работает, но: 1) лочит файлы
профиля, 2) синхронизация cookies устаревает, 3) уведомление "новое
устройство" всё равно может прилететь. CDP проще и надёжнее.
