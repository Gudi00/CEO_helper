## ⚖️ Этика и назначение

Проект сделан как **инженерная демонстрация навыков** в рамках стажировки EPAM: интеграция браузерного расширения с локальным бэкендом, каскад AI-провайдеров, парсинг DOM, WebSocket-обмен, работа с CDP. Это про архитектуру и инженерию, а не про оценки.

Использование инструмента на реальных оцениваемых тестах — целиком на ответственности пользователя и регулируется правилами учебного заведения. Репозиторий приватный и публикуется как часть портфолио.

## 📖 Описание

**СЭО helper** — гибрид из Chrome MV3-расширения и локального Python-бэкенда, построенный вокруг работы с тестами в Moodle (на примере [lms.bsuir.by](https://lms.bsuir.by/)). Расширение живёт в реальной пользовательской сессии браузера: оно разбирает вопрос прямо со страницы, отправляет его на локальный бэкенд, а тот обращается к AI-каскаду (Gemini Pro как основной провайдер, локальная Gemma/Ollama как fallback) и возвращает ответ. История попыток хранится в SQLite.

Инструмент поддерживает три режима работы: **подсказчик** (assist — просто показывает вариант), **пошаговое подтверждение** (step-by-step — ждёт твоего согласия) и **полный автомат** (full-auto). Бэкенд работает только локально (`127.0.0.1`), наружу из приватных данных ничего не уходит, кроме самого текста вопроса в выбранный AI-провайдер.

## 💡 Как появилась идея

Задача-вызов на стажировке: собрать систему, в которой браузерное расширение и «тяжёлый» Python-бэкенд работают в связке, а сверху — каскад AI с фолбэком на локальную модель. Moodle-тесты оказались удобным реальным полигоном: живой DOM, который надо надёжно парсить, разные типы вопросов, необходимость аккуратно общаться между content-script, service-worker и бэкендом. Получился цельный инженерный кейс — от разбора страницы до WebSocket-стрима ответов и хранения истории.

## 🛠 Технологический стек

| Технология | Для чего используется |
|------------|-----------------------|
| Python 3.12 + FastAPI | Локальный бэкенд: API, оркестрация |
| Uvicorn | ASGI-сервер |
| SQLAlchemy 2.0 + Alembic | Хранение истории попыток (SQLite), миграции |
| google-genai (Gemini) | Основной AI-провайдер |
| Ollama (Gemma / DeepSeek) | Локальный AI-fallback |
| Selenium + CDP | Engine-режим автоматизации браузера |
| TypeScript + Vite | Chrome MV3-расширение |
| Chrome Extensions MV3 | content-script, service-worker, popup |
| httpx, pydantic-settings | HTTP-клиент и конфигурация |

### ⭐ Нестандартные решения

| Решение | Что даёт |
|---------|---------|
| **Каскад AI-провайдеров** | Сначала Gemini, при недоступности/таймауте — локальная Gemma через Ollama; система не зависит от одного облака |
| **Расширение в живой сессии** | Работа в реальной вкладке пользователя, без отдельного headless-браузера — естественное поведение страницы |
| **Локальный бэкенд по токену** | Бэкенд слушает только `127.0.0.1`, токен генерируется при первом старте и хранится в `~/.config/lms-tool/` |
| **Единый парсер на двух сторонах** | Разбор вопроса и хеширование есть и в расширении (TS), и в бэкенде (Python) — для сверки и истории |

## 🚀 Установка и запуск

### Требования

- Python 3.12+
- Node.js (для сборки расширения)
- Chrome / Chromium
- (Опционально) Ollama с моделью Gemma для локального fallback
- Ключ Gemini API

Пошагово, от установки до первой подсказки: **[docs/QUICKSTART.md](docs/QUICKSTART.md)**. Подробности — в [docs/INSTALL.md](docs/INSTALL.md).

Коротко:

```bash
git clone https://github.com/Gudi00/a_SEO_bot.git
cd a_SEO_bot

sh scripts/install.sh       # Windows: scripts\install.bat · macOS: scripts/install.command
lms-tool doctor             # что настроено и что осталось сделать
sh scripts/start.sh         # сервер + код сопряжения (Windows: scripts\start.bat)
```

Дальше в Chrome: `chrome://extensions` → включить Developer mode → **Load unpacked** → выбрать `extension/dist`, затем ввести в окне расширения код сопряжения из окна сервера.

Источником ответов может быть Gemini, любой OpenAI-совместимый API (OpenRouter, DeepSeek, Groq, LM Studio), локальная модель через Ollama или **ручной режим** — без сервера и ключей.

### AI-каскад

`ai/cascade.py` оркестрирует провайдеров: запрос идёт в Gemini (`ai/gemini.py`), и если облако недоступно или превышен таймаут — управление переходит к локальной Gemma через Ollama (`ai/ollama.py`). Общий интерфейс задан в `ai/base.py`, промпты вынесены в `ai/prompts.py`.

### Связь расширения и бэкенда

Content-script разбирает вопрос (`moodle-parser.ts`), передаёт его через service-worker на локальный бэкенд (`api-client.ts`), а ответ возвращается тем же HTTP-запросом. Один и тот же вопрос хешируется на обеих сторонах, чтобы сверять и складывать историю.

### Companion-приложение

В папке `google_form_app/` лежит независимый продукт — мобильное Flutter-приложение для Google Forms, работающее полностью на устройстве с Gemini, без серверного бэкенда. У него свой README.

Полная архитектурная документация — в `docs/` (обзор системы, ROADMAP, dev-окружение, 10 ADR, спецификации API).

## 🧗 Трудности при разработке

### Три стороны, которые должны договориться

В MV3 content-script, service-worker и бэкенд живут в разных контекстах с разными ограничениями. Наладить надёжный обмен сообщениями между ними — и при этом стримить ответы по WebSocket — оказалось самой кропотливой частью. Помог единый слой типов и messaging-client на стороне расширения.

### Каскад, который не должен застревать

AI-провайдеры ведут себя по-разному: облако может тормозить или отвалиться. Чтобы система не зависала, каскад работает с таймаутами и чётким фолбэком на локальную модель — лучше быстрый ответ от Gemma, чем бесконечное ожидание Gemini.

### Живой DOM Moodle

Разметка вопросов в Moodle неоднородна, и парсер должен переживать разные типы заданий. Пришлось держать разбор и хеширование согласованными в двух реализациях — TypeScript в расширении и Python на бэкенде.
